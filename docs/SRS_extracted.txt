1. Introduction
1.1 Purpose and Intended Audience
This Software Requirements Specification (SRS) establishes a complete, unambiguous, and verifiable specification of requirements for the MSME360 platform—an integrated web-based business management and analytics system tailored for Micro, Small, and Medium Enterprises (MSMEs). This document serves as the authoritative technical agreement among software engineering students, academic project evaluators, faculty supervisors, and future maintainers.
The primary intended audience comprises: (1) Senior Software Engineers and Technical Reviewers evaluating architectural consistency, data integrity protocols, and API contracts; (2) Quality Assurance (QA) and Test Engineers constructing verification suites, automated integration tests, and acceptance test plans; (3) Academic Project Guides and Evaluators reviewing compliance with academic milestones across Database Management Systems (DBMS), Design and Analysis of Algorithms (DAA), Software Engineering (SE), and Web Technology (WT); and (4) MSME Business Stakeholders seeking operational transparency into how core inventory, procurement, sales, and accounting workflows are centralized.
1.2 System Scope and Objectives
MSME360 provides a cloud-native, responsive Single Page Application (SPA) backed by high-performance asynchronous RESTful web services. The platform is designed to overcome the severe operational hurdles documented across the MSME sector—where enterprises collectively contribute over 30% of national GDP, 45% of manufacturing output, and employ 110+ million workers, yet remain crippled by fragmented software tools, manual ledger entry, and delayed visibility.
Core Objectives: The primary objectives of the MSME360 system encompass:
Unified Operations Management: Consolidate inventory tracking, supplier purchasing, sales invoicing, customer CRM, general ledger accounting, and workforce management into a single unified cloud repository.
Granular Security Governance: Enforce strict Role-Based Access Control (RBAC) protocols utilizing JSON Web Tokens (JWT) and modern password hashing to govern access across business owners, store managers, and front-desk staff.
Transactional Data Integrity: Execute dual-sided atomic database transactions ensuring zero drift between physical stock counts, stock movement audit trails, and revenue/expense ledger entries.
Actionable Business Intelligence: Deliver dynamic operational intelligence through automated low-stock reorder point algorithms, stock velocity categorization, debtor aging buckets, and real-time interactive business dashboards.
1.3 Project Boundaries and Explicit Scope Exclusions
To maintain strict engineering feasibility within the academic timeline while ensuring industrial-grade implementation quality, the system boundaries for the current project release (Version 1.0) are explicitly defined. Capabilities not scheduled for delivery are cataloged below to prevent scope ambiguity.
[EXPLICIT SCOPE BOUNDARY] The current scope release of MSME360 focuses exclusively on internal operational management, inventory control, billing ledger recording, and business analytics. Direct financial settlements through commercial payment gateways (e.g., live Razorpay/Stripe webhooks) and automated submissions to government taxation portals (e.g., GSTN e-filing, live e-Way Bill generation) are strictly outside the Version 1.0 project boundary. All sales and purchases generate internal accounting ledgers and receipts, but external payment settlement is treated as external manual cash, bank transfer, or offline reconciliation.
Explicit Scope Exclusions (Version 1.0):The following modules and integrations are explicitly excluded from the current baseline:
Live Banking & Payment Gateway APIs: No live settlement transactions with external acquiring banks or card networks are executed within the application.
Direct Government Tax Portal Integration: Tax rates (GST/VAT) are computed and tracked within internal invoices and reports, but automated cryptographic signing and transmission to taxation authorities are deferred.
Automated Statutory Payroll Withholding: Basic employee compensation records and departmental salaries are tracked, but complex multi-tier statutory withholdings (PF, ESI, professional tax slabs) are not automated.
Offline-First Progressive Web App (PWA): The web application requires active network connectivity to synchronize with the centralized REST API; offline caching with background service workers is reserved for future versions.
Deep Learning Demand Forecasting: Dynamic Reorder Points and Stock Velocity are computed deterministically; deep neural network predictive forecasting using external macroeconomic regressors is outside the current scope.

2. Overall Description
2.1 Product Perspective and Architectural Spectrum
MSME operations are historically plagued by a stark technological divide. At the top end, Enterprise Resource Planning (ERP) systems (e.g., SAP S/4HANA, NetSuite) offer comprehensive operational coverage but impose prohibitive licensing expenditures, multi-month deployment cycles, and steep learning curves that alienate lean small business teams. Conversely, modular SaaS suites (e.g., Zoho, Odoo) introduce escalating recurring subscription costs and cross-module synchronization latency. Consequently, the vast majority of MSMEs revert to isolated desktop billing utilities (e.g., Tally Prime, Busy) or manual spreadsheets (Microsoft Excel, Google Sheets). These desktop tools operate as disconnected data silos lacking native cloud multi-user collaboration, while spreadsheets are notoriously prone to silent data corruption, lack audit trails, and provide zero referential integrity.

System Architecture Perspective: Architecturally, MSME360 is engineered as a modern, decoupled three-tier web application:
Presentation Tier (Client): Implemented as a responsive Single Page Application (SPA) utilizing React 18, Vite, TypeScript, and Tailwind CSS. The presentation layer handles local input validation, dynamic component rendering, and asynchronous HTTP communication via Axios/Fetch.
Application & Security Tier (Server): Powered by Python 3.12 and the FastAPI asynchronous framework. It implements RESTful API routing, strict request/response data validation via Pydantic models, role-based dependency injection guards, and atomic business orchestration.
Data & Analytics Tier (Storage): Anchored by a PostgreSQL relational database operating in Third Normal Form (3NF) with foreign key cascading rules and composite B-tree indexes. Database migrations are version-controlled via Alembic, while object persistence is mediated through SQLAlchemy 2.0 ORM. Real-time analytics are processed through dedicated analytical query aggregators.
2.2 High-Level Product Functions
The MSME360 platform consolidates eight core operational subsystems into a cohesive operational workflow:
1. Authentication & Security: Centralized JWT-based authentication with bcrypt password encryption and role-gated route middleware.
2. Product Catalog Management: Hierarchical category classification, product cataloging, SKU assignment, and dual-pricing (cost vs. selling).
3. Inventory & Stock Control: Real-time stock level monitoring, threshold alerts, and an immutable audit ledger of all movements (Purchases, Sales, Adjustments, Returns).
4. Procurement & Purchases: Supplier tracking, multi-item purchase order generation, automated unit cost recalculation, and stock replenishment.
5. Sales & POS Engine: Customer checkout terminal, multi-item invoicing, tax and discount computations, and immediate atomic stock decrements.
6. Customer Relationship Management: Customer profiles, contact registries, purchase histories, and cumulative lifetime spending analytics.
7. Finance & Accounting: Automated income/expense transaction logging, gross and net profit tracking, profit margin calculations, and receivables/payables tracking.
8. Workforce Administration: Employee roster maintenance, departmental assignments, salary records, and internal role provisioning.
9. BI & Reporting Engine: Dynamic executive dashboards, sales velocity trend charts, automated stock alert evaluations, and structured CSV/JSON report exports.

2.4 Operating Environment and Target Infrastructure
MSME360 is engineered to operate across modern distributed cloud infrastructure while maintaining a lightweight footprint capable of local workstation execution during academic demonstration and testing.
Application Server: Python 3.12+ 64-bit runtime environment running the Uvicorn ASGI server. Containerized via multi-stage Docker images to guarantee reproducible execution across Linux (Ubuntu 22.04 LTS / Debian 12) and Windows 11 environments.
Database Engine: PostgreSQL 15+ relational database with standard connection pooling. For rapid local testing and CI/CD automation, the architecture supports an in-memory repository implementation adhering strictly to identical interface contracts.
Client Web Browser: Compiled modern JavaScript (ES2022) bundle executed in modern evergreen web browsers: Google Chrome (v110+), Mozilla Firefox (v110+), Microsoft Edge (v110+), and Apple Safari (v16+). Minimum supported viewport: 1024x768 pixels.
Production Cloud Hosting: Containerized backend deployment targeting Render Cloud Web Services; frontend static SPA hosted via Vercel Edge Network with SSL termination.

3. System Features and Functional Requirements
This section details the functional requirements of the MSME360 platform, partitioned across nine cohesive operational modules. Each module is documented with its operational context, participating actors, preconditions, triggers, step-by-step main workflows, alternative and exception flows, postconditions, and atomic requirement statements adhering to the ISO/IEC/IEEE 29148 standard. Requirement statements utilize the mandatory normative keyword 'shall' and are assigned stable, traceable identifiers (FR-001 through FR-052) alongside MoSCoW priorities.
3.1 Module 1: Authentication, Authorization & User Management
Module 1 governs identity verification, cryptographic session management, and role-based operational gating across all system functions.
Participating Actors: System Administrator (ADMIN), Business Owner (OWNER), Store Manager (MANAGER), Sales Staff (STAFF).
Preconditions: User account exists in persistent storage with an active status flag (`is_active = True`) and a bcrypt-hashed password.
Trigger: User submits authentication credentials (username and plaintext password) via the web login interface.
Main Success Scenario: 1. Client POSTs credentials to `/api/auth/login`. 2. System retrieves user record by username. 3. System verifies plaintext password against stored cryptographic hash using `passlib.pwd_context` (bcrypt). 4. System generates a signed JWT bearer token containing `sub` (username), `role`, and expiration timestamp (24 hours). 5. System returns token and serialized user profile. 6. Client stores token and includes it in subsequent HTTP `Authorization: Bearer <token>` headers.
Alternative Flows: A1: Active token exists on client startup; client sends GET `/api/auth/me` to refresh user context without prompting for password.
Exception Flows: E1: Username not found or password verification fails → System returns HTTP 401 Unauthorized with error code `INVALID_CREDENTIALS`. E2: User account is deactivated (`is_active = False`) → System returns HTTP 403 Forbidden. E3: Expired or cryptographically tampered token presented → System returns HTTP 401 Unauthorized.
Postconditions: Authenticated session is established; API gateway enforces role permissions based on decoded token claims.

3.2 Module 2: Product Catalog & Category Taxonomy
Module 2 manages master product definitions, hierarchical category classifications, unit pricing, and stock monitoring thresholds.
Participating Actors: ADMIN, OWNER, MANAGER (Write/Edit); STAFF (Read-only).
Preconditions: Target category must exist prior to associating a product. User must possess MANAGER, OWNER, or ADMIN role.
Trigger: User navigates to Inventory page and initiates category or product creation.
Main Success Scenario: 1. User enters product name, unique SKU, category ID, cost price, selling price, opening stock, and minimum stock threshold. 2. Client submits POST `/api/inventory/products`. 3. System validates SKU uniqueness, positive pricing constraints, and category existence. 4. System persists product record and initializes stock balance. 5. System logs initial movement audit record. 6. System returns HTTP 201 Created with complete product payload.
Alternative Flows: A1: Product updated via PUT `/api/inventory/products/{id}` with modified prices or reorder thresholds.
Exception Flows: E1: Duplicate SKU submitted → System returns HTTP 400 Bad Request with code `DUPLICATE_SKU`. E2: Non-positive price submitted (`cost_price <= 0` or `selling_price <= 0`) → System returns HTTP 422 Unprocessable Entity. E3: Non-existent category ID supplied → System returns HTTP 404 Not Found.
Postconditions: New product is active in the catalog and available for procurement and sales transactions.

4. External Interface Requirements
4.1 User Interfaces & Viewport Ergonomics
The MSME360 user interface is delivered as a modern Single Page Application (SPA) styled with Tailwind CSS utility classes and Lucide React iconography. The UI adheres to an ergonomic dual-panel layout: a persistent collapsible vertical navigation sidebar on the left and a responsive content viewport on the right, capped by a top navigation bar.
Screen Hierarchy & Layout Specifications: The interface incorporates eight primary operational views:
1. Executive Business Dashboard (`/dashboard`): Features four high-visibility metric summary cards displaying Today's Revenue, Monthly Sales Volume, Low Stock Alerts, and Gross Profit Margin. Incorporates interactive sales velocity trend lines (Recharts) and top-product stock tables.
2. Inventory & Stock Management View (`/inventory`): Presents a searchable, paginated data grid of all catalog products with real-time stock counts, category tags, cost vs. selling prices, and color-coded status badges (Green = In Stock, Amber = Low Stock, Red = Out of Stock). Includes a modal for product creation/editing and manual stock adjustments.
3. Sales Terminal & Invoicing View (`/sales`): Optimized for rapid checkout. Features product search, quantity selectors, dynamic line-item calculation, customer selection/guest toggle, tax rate input, discount controls, and an immediate receipt generator.
4. Procurement & Purchases View (`/purchases`): Supplier purchase order generation interface, Goods Received Notes (GRN) logging, line-item cost tracking, and chronological purchase order history.
5. Customer Relationship Management (`/customers`): Customer directory with live search by name/email, lifetime spend metrics, contact information editing, and historical order inspection drawers.
6. Financial Health & Accounting Ledger (`/finance`): Restricted to ADMIN and OWNER. Displays revenue breakdown, operational expense tallies, net profit calculation, receivables, payables, and detailed financial transaction ledgers.
7. Workforce & Human Resources (`/employees`): Staff roster, departmental allocations, operational role badges, monthly salary baselines, and employee provisioning modals.
8. Business Intelligence & Reports View (`/reports`): Customizable date-range report generator with category filtering, automated alert feed (Critical/Warning), and one-click CSV and JSON data export buttons.
4.2 Hardware Interfaces
MSME360 does not require proprietary embedded hardware. It interfaces with standard commercial off-the-shelf (COTS) retail hardware devices via standard operating system drivers:
Workstation Hardware: Desktop PCs, laptops, and tablets equipped with minimum 1024x768 display resolution and standard input peripherals (mouse/touchpad/keyboard).
Barcode Scanners: Standard USB or Bluetooth barcode scanners operating in Human Interface Device (HID) keyboard emulation mode. Scanners input SKU strings directly into active search and sales item text fields.
Receipt & Invoice Printers: Standard thermal receipt printers (58mm/80mm ESC/POS compatible) and standard office laser/inkjet printers via standard browser print dialogues (`window.print()`).
4.3 Software Interfaces & Data Exchange
MSME360 establishes well-defined software interfaces across internal application tiers and external host infrastructure:
Frontend-Backend REST Interface: The React 18 client interfaces with the backend via stateless RESTful JSON APIs adhering to OpenAPI 3.1 specifications. All requests include standard HTTP headers (`Content-Type: application/json`, `Authorization: Bearer <jwt>`).
Database Engine Interface: The FastAPI backend interfaces with PostgreSQL 15+ using the SQLAlchemy 2.0 Object-Relational Mapper over asynchronous connection pools. Schema migrations are strictly governed by Alembic migration scripts.
Containerization & Cloud Hosting: The entire application is containerized using multi-stage Dockerfiles. The backend targets Linux-based container hosts on Render Cloud Web Services; static frontend assets are served via Vercel Edge CDN.
4.4 Communication Interfaces & Protocols
All data communication across client and server boundaries is governed by industry-standard networking protocols:
Transport Layer Security: All external HTTP traffic is encrypted using Transport Layer Security (TLS 1.3 / HTTPS). Insecure HTTP requests are automatically upgraded or rejected.
CORS Governance: Cross-Origin Resource Sharing (CORS) middleware is configured on the FastAPI server to whitelist authorized frontend origins while blocking unauthorized third-party domains.
Message Formatting: All request and response bodies utilize UTF-8 encoded JSON formatting, with strict Pydantic schema validation preventing malformed payloads from reaching internal business logic.

6. Data Requirements and Schema Architecture
6.1 Logical Data Model & Entity Relationship Architecture
The MSME360 relational database architecture is strictly normalized to Third Normal Form (3NF) to eliminate data redundancy and prevent update anomalies across high-frequency transactional workflows. Referential integrity is maintained through foreign key constraints with explicit cascading delete or set-null rules.
Core Relational Entities: The logical entity structure comprises fourteen core domain entities:
Users & Roles: Defines system operators, contact emails, cryptographic password hashes, and assigned operational roles.
Categories & Products: Hierarchical taxonomy groups governing individual inventory items.
Stock Movements: Immutable chronological audit log capturing every quantity delta across purchases, sales, adjustments, and returns.
Customers & Suppliers: Commercial client profiles and procurement vendor registries.
Purchases & Sales (Orders & Items): Master transaction records and normalized line-item child tables detailing quantities, unit prices, and subtotals.
Financial Transactions: General financial ledger recording all atomic income and expense entries tied to business receipts.
Employees & System Alerts: Internal workforce roster and dynamic inventory warning notices.

6.3 Data Validation Rules and Integrity Constraints
The database layer and Pydantic validation schemas enforce rigid operational integrity rules:
Non-Negative Bounds: All monetary prices (`cost_price`, `selling_price`), financial transaction amounts, and employee salaries must be strictly positive numerical floats (`value > 0`). Line item quantities must be positive integers (`quantity > 0`).
Stock Floor Enforcement: Physical inventory balances (`stock_quantity`) cannot fall below zero under any operational circumstance. Any transaction attempting to decrement stock below zero is aborted immediately.
Cascading Referential Integrity: Foreign keys from child tables (e.g., `sale_items.product_id`) reference valid parent records. Deleting a parent category or product with active transaction history is prohibited (RESTRICT) to prevent orphaned historical records.
Indexing Strategy: Composite B-tree indexes are deployed across `(tenant_id, created_at, sku)` to optimize range queries, sales filtering, and real-time dashboard aggregations.
6.4 Storage, Retention, and Archival Guidelines
Operational data retention protocols ensure audit compliance and database longevity:
Immutable Financial Records: Sales orders, purchase receipts, stock movements, and financial ledger entries are preserved indefinitely as permanent immutable business records.
Soft Deletion Strategy: Products, categories, customers, and employees utilize soft deactivation (`is_active = False`) rather than physical deletion (`DELETE`), ensuring historical sales invoices resolve accurately.
Backup Cadence: Automated database backups (full snapshots daily, Write-Ahead Log WAL archiving hourly) are maintained with a rolling 30-day recovery window.
6.5 Data Import and Export Formats
MSME360 supports structured data interchange via standard CSV (RFC 4180) and JSON (RFC 8259) specifications. Exported sales and inventory reports include metadata headers, ISO-8601 UTC timestamps, and normalized numerical columns formatted for immediate analysis in external spreadsheet software.

8. System Constraints, Assumptions, and Limitations
8.1 Mandatory Technical & Architectural Constraints
The technical architecture of MSME360 is bound by non-negotiable engineering constraints:
Framework Constraint: The backend must be implemented using Python 3.12+ and the FastAPI asynchronous framework, exposing stateless RESTful JSON endpoints.
Relational Persistence Constraint: The target production database must be PostgreSQL 15+, normalized to Third Normal Form (3NF) and managed via Alembic version-controlled migrations.
Frontend Presentation Constraint: The frontend must be constructed as a Single Page Application (SPA) using React 18, Vite build tooling, and Tailwind CSS for utility-first styling.
Cryptographic Protocol Constraint: All user authentication must utilize standard OAuth2 Bearer password flow issuing signed JSON Web Tokens (JWT) using the HS256 algorithm.
Academic Milestone Alignment: The architecture must strictly align with the academic syllabus across Database Management Systems (DBMS), Design and Analysis of Algorithms (DAA), Software Engineering (SE), and Web Technology (WT).
8.2 Validated Engineering Assumptions
The functional design assumes the following validated environmental parameters:
Operational Connectivity: Network latency between client browsers and backend cloud services does not exceed 250ms under normal operating conditions.
Client Runtime Environment: Client workstations operate modern evergreen web browsers with full ES2022 JavaScript, LocalStorage, and CSS Flexbox/Grid support enabled.
User Operational Security: Users adhere strictly to credential confidentiality protocols; session tokens are stored securely in browser session contexts.
8.3 Known Implementation Limitations of the Current Baseline
To ensure academic transparency and implementation clarity, known limitations of the Version 1.0 baseline are documented:
1. In-Memory Prototype Persistence: The prototype utilizes an in-memory repository layer for instantaneous test execution and local demonstration. While functionally identical in business logic and atomic behavior, enterprise deployment requires binding the SQLAlchemy PostgreSQL connection string.
2. Cash / External Payment Settlements: All sales transactions record internal billing receipts and income ledgers, but direct external payment gateway capture (Razorpay/Stripe) is not executed in Version 1.0.
3. Online Cloud Connectivity Requirement: The system requires active network connectivity; offline transactional queueing with client-side SQLite/IndexedDB synchronization is deferred to future releases.
4. Synchronous Alert Engine: Inventory alerts are evaluated synchronously upon API request; an independent asynchronous background message queue (e.g., Celery/Redis) is targeted for Version 2.0.
